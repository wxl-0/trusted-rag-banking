# 可信 RAG 银行业监管问答系统：验收方案

## 1. 文档定位

本文档定义当前版本是否达到产品交付标准。验收覆盖身份权限、个人对话、知识库维护、异步入库、可信问答、部署和故障安全，不用 AI 正确率替代产品功能验收。

评测质量见[评测方案与结果](评测方案与结果.md)，需求、实现、测试和提交的对应关系见[需求追溯矩阵](需求追溯矩阵.md)。

本文档中“历史验收结果”来自对应 Issue 的已发布验收记录；“本次文档检查”只证明文档和链接，不等同于重新执行真实全栈业务验收。

## 2. 验收目标

1. 两类业务角色可以按权限完成各自任务；
2. 个人对话和知识库业务状态可以持久化；
3. 上传资料能够安全、异步、可恢复地进入当前可检索知识；
4. 问答能够返回可核验证据，并在证据不足时安全拒答或澄清；
5. 关键依赖、服务、前端和数据链路可以通过明确步骤验证；
6. 文档只声明经过验证的当前能力，并列出已知限制。

## 3. 验收范围

### 3.1 包含

- PostgreSQL、Keycloak、Redis、MinIO、Qdrant、API、Worker 和 React 前端；
- 企业成员和知识库维护者两类业务角色；
- 个人对话、滚动摘要、问答和证据查看；
- 知识文档列表、批量上传、原件下载和逻辑撤回；
- 单文档解析、Qdrant/BM25 构建、原子发布和任务恢复；
- 制度问答、报表取数、比较计算、多轮追问和拒答；
- 自动化测试、前端生产构建、Compose 服务和人工业务烟雾验收。

### 3.2 不包含

- 多租户、个人知识库和企业身份源正式集成；
- 同文档替换上传和版本浏览；
- 维护者手工重试；
- 永久物理清理和数据保留策略；
- 未经重新运行的私有全量评测结果更新；
- 生产级容量、压测、灾备和安全渗透测试。

## 4. 验收环境与前置条件

### 4.1 环境

- Python 和依赖以 `pyproject.toml`、`uv.lock` 为准；
- 前端依赖以 `src/frontend/package-lock.json` 为准；
- 完整服务由 `docker-compose.yml` 编排；
- 真实 PostgreSQL 集成测试只允许使用名称以 `_test` 结尾的可丢弃数据库；
- 真实问答需要合法的模型、Embedding、Reranker 和自备知识资料。

### 4.2 前置条件

1. `.env` 已由使用者在本地配置，真实凭据未写入 Git；
2. Keycloak 中存在企业成员和知识库维护者测试身份；
3. 测试知识资料已依法准备，格式和大小满足上传限制；
4. Qdrant、MinIO、Redis 和 PostgreSQL 使用隔离的测试或演示数据；
5. 执行人知道私有评测资产不属于公开仓库可复现内容。

## 5. 分层验收策略

| 层级 | 证明内容 | 不能证明的内容 |
| --- | --- | --- |
| 单元/模拟测试 | 模块规则、错误分支和接口契约 | 真实外部依赖和真实模型可用性 |
| PostgreSQL 集成测试 | 迁移、约束、事务和持久化结果 | 完整浏览器和外部模型链路 |
| 前端测试与构建 | 客户端状态、交互逻辑和可生产构建 | 后端真实入库完成 |
| Compose 就绪检查 | 服务和必要依赖达到就绪状态 | 最终业务问答一定正确 |
| 浏览器业务验收 | 两类角色完成完整用户流程 | 私有全量评测指标不退化 |
| 正式/专项评测 | 指定快照下的 AI 效果 | 所有产品功能和生产稳定性 |

任何一层通过都不能替代其他层。

## 7. 执行命令

### 7.1 后端与通用测试

```bash
uv sync --frozen
uv run --frozen python -m pytest tests/ -v
```

### 7.2 真实 PostgreSQL 集成测试

```bash
docker compose --profile test up -d --wait postgres-test
TRUSTED_RAG_TEST_DATABASE_URL=postgresql+psycopg://trusted_rag_test:trusted_rag_test@localhost:5433/trusted_rag_test \
  uv run --frozen python -m pytest tests/ -v
docker compose --profile test stop postgres-test
docker compose --profile test rm -f postgres-test
```

### 7.3 前端

```bash
cd src/frontend
npm ci
npm test
npm run build
```

### 7.4 完整 Compose

```bash
docker compose up -d --build --wait
curl --noproxy localhost http://localhost:8000/api/health
curl --noproxy localhost http://localhost:8000/api/ready
```

健康检查成功只证明服务状态，之后仍需执行 AC-35 浏览器业务烟雾流程。

### 7.5 Pull Request CI

`.github/workflows/ci.yml` 在 Pull Request 和 `main` 分支推送时执行三组检查：

1. Python 3.12、锁定依赖和临时 PostgreSQL `_test` 数据库上的后端测试；
2. Node 22、`npm ci`、前端测试和生产构建；
3. Markdown 相对链接、代码围栏和行尾空白检查。

CI 不下载业务模型、不调用真实生成接口，也不包含私有正式题集、专项题集或 Bad Case 明细。私有资产缺失时，资产完整性测试必须明确 `skip`；这表示该项未在干净克隆复核，不能解释为私有评测通过。

## 9. 验收通过标准

发布前需要同时满足：

1. 与改动相关的自动化测试通过；
2. 后端全量测试和前端测试/生产构建通过；
3. 涉及数据库时，真实 `_test` PostgreSQL 迁移和集成测试通过；
4. 涉及部署或跨服务时，Compose 就绪和浏览器业务烟雾通过；
5. 涉及 RAG 效果时，定向 Bad Case 回归通过；需要宣称新指标时重新运行对应评测；
6. README、`CONTEXT.md`、产品/技术/评测文档与实际能力一致；
7. 不提交真实凭据、私有资料、Chunk、索引和私有逐题报告；
8. 已知限制和未执行验证明确记录。

## 10. 当前验收结论与限制

历史证据表明，当前版本已经完成身份、个人对话、在线知识维护、版本化入库、可信问答和完整演示链路的阶段验收。

以下事项不应被描述为已验收生产能力：

- 统一硬件矩阵下的容量和性能指标；
- 生产流量下的并发稳定性；
- 完整灾备、渗透测试和正式安全认证；
- 维护者手工重试和永久物理清理；
- 同文档版本浏览、替换上传和业务回滚；
- 后续代码变化在没有重跑时自动保持历史评测指标。
