# ADR-001：使用 PostgreSQL 作为业务事实源

- 状态：已采纳
- 日期：2026-08
- 关联 Issue：[#1](https://github.com/wxl-0/trusted-rag-banking/issues/1)、[#2](https://github.com/wxl-0/trusted-rag-banking/issues/2)、[#8](https://github.com/wxl-0/trusted-rag-banking/issues/8)、[#12](https://github.com/wxl-0/trusted-rag-banking/issues/12)

## 背景

系统从一次性命令行建库扩展为企业长期使用的知识工作台后，需要持久保存：

- 个人对话、消息、回答证据和滚动摘要；
- 知识文档、不可变版本和当前版本；
- 异步入库任务、状态、租约和失败结果；
- 活动 BM25 代际和发布指针；
- 上传、撤回等重要操作的审计事实。

Redis、MinIO、Qdrant 和本地 BM25 文件都可能独立故障、重启或存在暂存产物，不能让任一组件单独决定业务当前状态。

## 决策问题

企业化能力应由哪个组件保存最终业务事实，并协调对话、文档、任务和索引状态？

## 候选方案

### 方案 A：让各组件分别保存自己的状态

- Redis 保存任务状态；
- MinIO 对象存在表示文档存在；
- Qdrant 中的点表示版本可检索；
- BM25 文件名表示活动代际。

优点是开发初期简单。缺点是发生部分成功或服务重启时，没有一个位置能够回答“哪个版本才是当前有效业务状态”。

### 方案 B：以 Redis 为任务和发布事实源

Redis 适合短期队列和协调，但不适合作为必须长期审计、迁移和关联查询的业务事实源。缓存丢失或过期会使任务状态和版本关系不可追溯。

### 方案 C：以 PostgreSQL 为业务事实源

PostgreSQL 保存业务对象、状态和活动指针，其他组件只保存专用产物。业务决策通过数据库事务和约束落地。

## 决策

采用方案 C：PostgreSQL 是用户引用、个人对话、知识文档、文档版本、入库任务、活动索引代际和审计事件的唯一业务事实源。

组件职责明确为：

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| Keycloak | 认证、角色、登录会话 | 业务文档和业务权限事实 |
| PostgreSQL | 业务对象、状态、关系、事务和审计 | 原始文件、向量和短期队列 |
| Redis | 队列、短租约、协调锁 | 最终任务和版本状态 |
| MinIO | 私有原件和不可变版本工件 | 业务归属和当前版本判断 |
| Qdrant | 向量索引候选和检索 | 原始文件和业务主数据 |
| BM25 | 关键词索引产物 | 活动代际的最终选择 |

数据库结构通过 Alembic 迁移维护，应用启动不得在生产环境静默建表或改变 Schema。

## 结果

### 正向结果

- 可以用事务维护当前版本和活动 BM25 代际；
- Worker 重启后能从数据库恢复排队或过期任务；
- 重复投递可通过唯一约束和任务幂等键收敛；
- 对话归属、逻辑删除和审计记录可追溯；
- Redis 或外部索引短暂故障不会抹掉业务事实。

### 代价

- 需要维护数据库迁移、事务、约束和连接可用性；
- 检索前需要读取或缓存当前版本集合；
- 外部产物与数据库状态之间必须设计补偿和清理；
- PostgreSQL 成为关键依赖，需要单独的备份和恢复策略。

## 不变量

1. Redis 消息存在不代表任务已经成功。
2. MinIO 对象或 Qdrant 点存在不代表版本已经发布。
3. 活动版本、任务终态和 BM25 活动代际只能由 PostgreSQL 业务状态决定。
4. 业务数据库不保存 Keycloak 密码、文件正文和向量数据。
5. 真实数据库集成测试只允许连接名称以 `_test` 结尾的可丢弃数据库。

## 重新评估条件

只有在以下情况才重新评估本决策：

- 系统扩展为多区域强一致部署，单 PostgreSQL 不能满足可用性目标；
- 业务状态规模和吞吐超出当前关系模型能力；
- 引入经过验证、能够提供同等事务、审计和迁移能力的替代事实存储。

在重新评估前，不得让 Redis、MinIO、Qdrant 或本地索引文件越权承担业务事实职责。
